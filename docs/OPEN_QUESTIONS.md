## 一、需要 A 确认（企微与 Agent）

### A1. A 怎么调用 B：同进程 import 还是 HTTP？

- **B 的建议：** 同进程 `from services import ...`。理由：同一个仓库、同一个 Python 进程，少一层网络和序列化；V4 也写的是「一个后端」。
- **影响：** 决定 A 要不要写 HTTP 客户端、要不要处理超时。
- **待确认：** A 是否有必须跑在独立进程的理由（例如企微 SDK 必须跑在特定事件循环里）。

### A2. 通知解析的字段由谁定义？

V4 分工是「A 解析、B 匹配」，但两边必须用同一套字段名。

- **B 的建议：** 由 B 在 `services/schemas.py` 里用 Pydantic 定义 `NoticeCandidate`（字段见 `API_CONTRACT.md` 3.x 与 4.5 节），A 按它填充后传给 `match_notice`。A 不自己另起字段名。
- **待确认：** A 的解析输出能否直接对齐这些字段；不能的话缺哪些。

### A3. 确认编号 `T03` 谁生成？

- **B 的建议：** B 生成（`previews.confirm_code`，用户范围内唯一、随预览过期失效），A 只回显，用户回「确认 T03」时 A 原样传给 B。
- **理由：** 编号必须和草稿状态绑定，A 生成无法保证不重复、不冲突。
- **待确认：** A 的对话里是否已经假设自己生成编号。

### A4. 追问话术由谁写？

- **B 的建议：** B 只返回 `questions[]`（字段名 + 原因码 + 建议问法），A 负责最终措辞和上下文衔接。
- **待确认：** A 是否接受「B 给建议问法、A 可改写」，还是希望 B 直接给整句。

### A5. 企微 `wecom_msg_id` 的可靠性

- **B 需要 A 保证：** 同一条消息重试送达时 `msg_id` 不变；A 在调用 `record_notice` 前不要自己先去重（B 用数据库唯一约束去重，A 侧去重只是优化）。
- **待确认：** 企微回调里这个 ID 的确切字段名与格式。

### A6. 看板链接的 token 谁签发？

- **B 的建议：** B 提供 `create_dashboard_token(user_id)`，A 拼成 `https://<看板>/?token=...` 返回。
- **待确认：** 看板地址（局域网 IP / 内网穿透 / 临时公网），以及链接有效期多久（B 默认 120 分钟）。

### A7. 消息时间与时区

- **B 的建议：** A 传 `received_at` 时统一转成 `2026-11-30T09:00:00+08:00`。
- **待确认：** 企微回调给的时间是 UTC 时间戳还是字符串。

### A8. 「发一下计划表」这类固定语句是否走模型？

V4 说这类可程序直接处理。**待确认：** A 侧哪些语句走规则、哪些走模型，B 需要知道调用量（决定每次最多 8 次工具调用的计数方）。

## 二、需要 C 确认（网页与演示）

### C1. Streamlit 走 HTTP 还是同进程 import？

- **B 的建议：** 走 HTTP（`http://127.0.0.1:8000/api/v1/...`）。理由：手机要访问、跨端要验证、也符合 V4「网页校验访问者与企微用户的绑定关系」。
- **代价：** C 要处理 token 和网络错误；同进程 import 更省事但无法验证手机访问。
- **待确认：** C 的选择。

### C2. 看板页面结构

V4 要求「手机可读的一个页面」：顶部下一节课/最近截止/待确认提示，中间按日期显示，下方待办。

- **B 的建议：** 直接消费 `GET /api/v1/dashboard` 一个接口，不自己拼多个接口。
- **待确认：** 这个结构是否够用；C 是否需要额外的「周视图」。

### C3. 待确认草稿怎么展示？

V4 要求「未确认的调整单独标记，不混进正式安排」。

- **B 的建议：** 顶部用 `pending_changes` 显示一条黄色提示条，点开看 `diff`（`/api/v1/previews/{id}`），正式时间轴只渲染 `plan.status='confirmed'` 的块。
- **待确认：** C 是否需要在网页上提供「确认」按钮（V4 说企微不可用时可用网页确认，是备用入口）。

### C4. 前后差异的展示粒度

- **B 的建议：** 按 `diff_json` 的 added / changed / removed / kept 四类分组显示，changed 显示「旧值 → 新值」。
- **待确认：** C 的 UI 能否直接吃这个 JSON，还是需要 B 再拍平成一句话。

### C5. 刷新方式

- **B 的建议：** 手动刷新按钮 + 每 5 秒轮询一次（Streamlit 用 `st_autorefresh` 或按钮）。演示时用按钮更可控。
- **待确认：** 演示时是否需要自动刷新。

### C6. 演示数据谁维护？

- **B 的建议：** B 写 `demo/seed.py`，一条命令重置成 12/6 场景；C 只读，不改数据，避免两人同时改数据导致演示翻车。
- **待确认：** C 是否需要额外的展示用字段（例如课程颜色）。

### C7. 手机访问地址

- **待确认：** 用局域网 IP 还是内网穿透（ngrok/frp）；如果企微里点开需要在手机网络下访问，本机 `127.0.0.1` 不行。这是**风险项**，V4 也专门提到「电脑上能打开、手机点不开」。

### T6. 演示数据与「固定今天」 —— ✅ 已实现（2026-11-20）

V4 要求固定 2026-11-30 上午。程序不能直接读系统时间，否则过几天演示就崩。

**实现方式：** `services/clock.py` 用环境变量控制两种模式：

| 变量 | 值 | 说明 |
|---|---|---|
| `UNIPULSE_TIME_MODE` | `real`（默认）/ `demo` | 用真实时间还是固定时间 |
| `UNIPULSE_DEMO_NOW` | `2026-11-30T09:00:00+08:00` | 仅 demo 模式使用，必须带时区 |
| `UNIPULSE_TIMEZONE` | `Asia/Shanghai` | 统一时区 |

业务代码统一调用 `from services.clock import get_now, get_today`，禁止 `datetime.now()`。
配置错误会抛 `ClockConfigError`，不会静默回退。
演示数据由 `python -m demo.seed` 写入。

- **剩余待确认：** 团队是否接受"用环境变量而不是配置文件"（B 已按此实现，改起来成本低）。
