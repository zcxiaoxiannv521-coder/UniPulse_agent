## 2. 差异表

| 项目 | B 的仓库草案 | C 的现有代码/草案 | 后续需确认 |
|---|---|---|---|
| 路径 | `/api/v1/dashboard` | `/v1/workspace` | 以团队统一契约实现读取适配 |
| 成功响应 | 直接返回 Dashboard | `{ok:true,data:{...}}` | 同时对齐错误响应，不能误判失败 |
| 用户 | `user.name` | `profile.display_name` | 转换只做展示，不从 user_id 参数取身份 |
| 计划 | `plan` + `days[].items` | `plans` + `study_blocks` + 依赖版本 | 旧块/草稿/正式计划必须继续区分 |
| 预览 | `pending_changes` 摘要、再取 Preview，diff 分 added/changed/removed/kept | `pending` 内含 changes / preserved | 补足详情与确认编号，不硬编码考试专用差异 |
| 时间缺口 | required / scheduled / gap_minutes | required / kept / unplaced_minutes | 数值由 B 求解，C 只映射展示 |
| 身份 | B 草案为签名链接 token，query/cookie 尚待三方确认 | 每个网页会话输入测试凭据，Bearer 转发 | 不能自行决定或把可转发链接当作本人身份验证完成 |
| 确认 | preview_id + expected_version | action_id，依赖版本存草稿 | 与 B 的原子写入/幂等约定统一 |
| 网页写入 | B 草案主要查询与备用确认 | C 演示另有手动课程/目标/反馈 | 正式端点和权限需 B 明确，不要求 B 直接照 C 草案新增 |
| 场景数据 | B 负责 demo/seed 与 SQLite | C 的独立 fixtures | 数据库联调时由 B 统一维护，不让 C 直接改 SQLite |
