# UniPulse 校园智能助手 Agent

**V4 开发方案与 AI 编程提示词｜3 人｜16 天冲刺**  
**开发：2026 年 11 月 20 日—12 月 5 日；计划 12 月 6 日提交，以赛事正式通知为准。**

> **企微里交代，网页上查看。** 把校园通知原文复制到企业微信机器人私聊，UniPulse 会整理出日程、待办和变更；说一句“发一下计划表”，机器人就回复个人工作台链接，点开看当前任务、课表和学习安排。

本文是开发方案，不是上线说明。文档提到的旧网页和效果图仅是原型，新增 Agent 能力与企微联动须按第六节实测。

**阅读建议：**第一次看先读第一、二节和演示；准备开工看第三、四、八节；用 AI 写代码时从第五节选一条任务提示词。

## 一、项目定位与首版范围

UniPulse 帮学生把散落在聊天里的校园通知，变成可查看、可更新的个人安排。**通知整理是日常入口，单门考试备考是比赛主场景**：用考试改期、临时调课或学习进度变化，证明 Agent 能维护同一个目标，而不只是提取通知或给一张静态计划表。

目标用户是在几个课程群里接收通知、要在课余安排复习的大学生。要解决的不是“通知看不懂”，而是**通知看懂了，还得手动对照课表、改待办、重新找空档**。UniPulse 让这些动作在同一个私聊里完成，网页只负责把结果摊开给学生看。

| 首版接收的通知 | 整理成什么 | 不擅自做什么 |
|---|---|---|
| 单次调课、停课或换教室 | 定位到具体一节课，给出时间或地点差异 | 不把某一次调课改成每周调课 |
| 考试安排或改期 | 建立或更新考试事件，核对关联备考计划 | 不从没有明确日期的资料里编造考试 |
| 作业或上交提醒 | 将明确要求整理为待办，保留截止和原文 | 不猜作业范围，也不替学生提交 |

| 优先级 | 做什么 |
|---|---|
| P0 必做 | 企微私聊收文本通知、识别并整理日程/待办；确认后更新数据；“发一下计划表”回复个人看板链接；单门考试的初始排程、局部重排与时间不足协商 |
| P1 有余力 | 主动提醒实际送达、日历导出、文字型 PDF/DOCX、基于反馈提出估时建议 |
| P2 后续 | 截图 OCR、重复跟进、多门考试统筹、更多校园事务 |

首版使用手动录入的具体日期课表和脱敏演示数据。不读取未授权群聊，不承诺接入正式教务系统，不做独立 App，也不把学习时长当作掌握程度。

## 二、两个端怎么配合

| 入口 | 主要用途 |
|---|---|
| **企业微信私聊（主入口）** | 贴通知、交代目标、补充信息、确认修改、反馈进度、索取计划表 |
| **个人网页（看板）** | 查看本周课表、考试与截止、待办和学习时间块；标明待确认调整、通知来源和当前计划版本 |

两端共用同一份数据。计划表链接指向**当前个人看板**，不是截图、附件或静态页面；确认修改后刷新即可看到新安排。用手机企微实测链接能打开；网页校验访问者与企微用户的绑定关系，不能凭链接里的用户编号读取数据。私人链接只在私聊返回。

网页首版做**一个手机可读的页面**即可：顶部显示下一节课、最近截止和待确认提示；中间按日期分开显示课程、考试和学习时间块；下方显示待办及进度。需要核对时展开通知来源和计划改动，不先做多层页面。用户从企微点进来，看到的是他刚刚交办的结果，不用再讲一遍。

企微不可用时，网页保留简版对话与确认入口用于备用演示；只演示实际跑通的环节，不把网页演示说成企微已接通。

### 一条完整的使用流程

1. **发通知。** 学生把老师发的调课、考试或作业通知原文粘贴到企微私聊，不必填表或上传文件。
2. **整理与追问。** Agent 提取课程、事项、日期、地点、截止和明确待办，匹配已有安排，并回复简短摘要。缺关键字段或遇到矛盾就追问，不猜日期或课程。
3. **确认变更。** 如果通知影响已有课表、考试或复习任务，先说明“原安排 → 新安排、影响什么、保留什么”。学生在企微确认后，再应用对应修改。
4. **打开计划表。** 学生说“发一下计划表”，机器人回复个人看板链接。点开看到同一份课表、任务和最新的已确认计划；未确认的调整单独标记，不混进正式安排。

### 企微对话示例：贴一条调课通知

以下是假想演示，具体时间和空档以测试课表为准：

| 谁发 | 消息 |
|---|---|
| 学生 | 【调课通知】机器学习课由 12 月 1 日 14:00–15:30 调到 12 月 2 日 10:00–11:30，教室不变。 |
| UniPulse | 找到这一次机器学习课。新时间与 12 月 2 日 10:30 的第三章复习冲突；建议将复习移到当日 14:00，其他课程和任务不变。回复“确认 T03”应用本次调整。 |
| 学生 | 确认 T03。 |
| UniPulse | 调课已记录，第三章复习已移到 12 月 2 日 14:00。 |
| 学生 | 发一下计划表。 |
| UniPulse | 打开我的计划表（回复真实个人看板链接）。 |

如果通知只写“下周改到上午”，机器人先问具体日期或时间。若当时没有合适空档，机器人可以先请学生确认调课事实，再显示“复习计划待调整”，而不是把课程和复习排在同一时间。

### Agent 为什么不只是解析通知

| 情况 | Agent 的下一步 |
|---|---|
| “帮我准备机器学习考试，每天最多 90 分钟” | 查考试、范围、课表与进度；只问必要缺口；找空档并生成计划预览 |
| 考试提前或单次调课 | 匹配受影响的事件和目标，只重排受影响、未开始且可移动的学习块 |
| “第三章只复习了一半” | 记录明确完成范围和剩余工作；已完成内容不重复安排。只报学习时长则不推断完成比例 |
| 时间不够 | 报告还有多少分钟排不进去，让学生选增加允许时段或减少指定选做内容，再重新检查 |
| 通知重复、过旧或仅改地点 | 去重或提示冲突，不回退日程；若地点变化不影响时间或通勤，不重排学习计划 |

## 三、技术方案与关键规则

### 3.1 一个后端、一个 Agent、两种界面

企微和网页共用 FastAPI 服务和 SQLite 数据库。网页用 Streamlit，输入输出用 Pydantic 校验。**模型负责读懂用户、选择业务工具、解释结果；Python 负责看时间、算冲突、查权限、按确认写入。** 首版不引入多 Agent、向量数据库或独立记忆服务。

```text
企微私聊 ──→ 可信身份与消息去重 ──┬─→ Agent 选工具：查上下文 / 解析 / 排程 / 预览
                                  ├─→ 明确确认：后端校验并提交
                                  └─→ 查计划表：返回个人看板链接
                                              │
手机网页 ───────────────→ 共享服务 ─────────→ SQLite
```

明显的“发一下计划表”或带编号的确认可由程序直接处理，不必每条消息都调用模型。需要判断的消息才交给 Agent，例如新通知是新增事项、某次调整，还是旧通知被再次转发。

### 3.2 企微接入顺序

1. **确认测试权限。** 先确认团队有可用的企业微信组织、可创建或使用的智能机器人，以及用于私聊测试的成员账号。机器人配置留在本地环境变量，不发到群里、不提交仓库。
2. **做固定回复。** 不需要下载整个 GitHub 仓库。准备好项目 Python 环境后，安装下方 SDK；按官方示例先做到手机私聊发“你好”，机器人回“收到”。这一步不接模型和数据库。
3. **验证跨端。** 用脱敏数据让“发一下计划表”返回测试看板链接；在手机企微里点开并测试权限。联调页面不要放真实学生数据，也不能把仅电脑本机可访问的地址当成手机测试已通过。
4. **再接业务。** 接入用户身份、消息去重、通知整理和实际更新；最后单独测试主动提醒。若企微权限暂时卡住，先用网页的备用入口继续验证业务，但把企微接入标为未通过。

```powershell
python -m pip install wecom-aibot-python-sdk
```

参考：[企微官方长连接文档](https://developer.work.weixin.qq.com/document/path/101463)、[官方 Python SDK](https://github.com/WecomTeam/wecom-aibot-python-sdk)。主动推送不作为“可以私聊回复”的前置条件，演示也不混淆这两件事。

### 3.3 业务工具和数据

以下是三人联调约定，不是已实现的接口。先对齐字段和结果，再分别编码：

| 工具或服务 | 输入 → 输出 | 负责人 |
|---|---|---|
| 上下文查询 | 当前目标和日期范围 → 考试、具体课表、剩余任务、偏好，附缺失项和版本 | B |
| 通知解析与匹配 | 通知文本 → 候选事项、原文证据、已有事件匹配或需要追问的问题 | A 解析、B 匹配 |
| 空档与排程 | 剩余任务、课表、截止和约束 → 时间块、未排入分钟和冲突原因 | B |
| 预览与提交 | 建议变更 → 确认编号、差异和有效期；确认后返回实际变更结果 | A 接交互、B 管数据 |
| 看板查询与链接 | 当前可信用户 → 本人课表、待办和有效计划；链接不触发重排 | A 回链接、B 提供查询、C 显示 |

模型工具可查询、解析和试算，生成的是候选结果或预览，**不能自行审批**。身份由后端从会话取得，不由模型从消息原文推断。工具执行失败要与“没有查到数据”分开；每次最多 8 次工具调用，同一目标串行，等待补充时保存状态，下次从原目标继续。

| 数据 | 必须保存的内容 |
|---|---|
| 用户与渠道 | 内部用户标识、企微绑定、时区、用户明确确认的偏好及作用范围 |
| 通知与事件 | 原文证据、接收时间、可得的发布时间、所属课程、具体事件时间和版本 |
| 目标、待办与时间块 | 考试关联、范围、剩余估时、任务进度；区分“要做什么”和“安排什么时候做” |
| 计划、预览与运行记录 | 当前生效版本、修改前后差异、依赖版本和确认有效期；保留调用摘要、消息去重和提醒状态 |

考试日期只从关联事件读取，不另存一份容易不同步的日期。初始目标、调整草稿和当前正式计划分开；网页不能把待确认草稿渲染成已生效安排。

### 3.4 排程、确认和失败处理

- **先算可用时段。** 首版覆盖未来七天，不越过考试和任务截止；扣除课表、考试、锁定活动与缓冲，在允许的学习时段内遵守每日上限。不确定的课表要提示补全，不能把所有空白默认当空闲。
- **保住原有工作。** 先保留已完成、已开始、锁定或不受影响的块，仅重排剩余且允许移动的部分。任务按截止和优先级分配，只对允许拆分的任务拆块；总空闲时长够，不代表有足够连续空档。
- **不足就说明缺口。** 比如还需 230 分钟，只排进 150 分钟，就显示余下 80 分钟及阻塞原因。让用户选择补充可用时间或减少指定选做范围，重新校验；不能自动挤占课程或降低必做要求。
- **确认后才改。** 预览保存旧值、新值、保留项、来源、依赖版本和有效期。只在后端验证用户、版本、约束后提交；重复确认返回已有结果，预览已过时就重新生成。取消只取消该草稿，不擅自回退之前已确认的事实。
- **写入后重查。** 计划、时间块和提醒失效在同一事务处理；失败不留下半套更新。考试已改期但新计划未确认时，标为“计划待调整”，旧提醒停用。回复区分未提交、已写入、提醒入队和消息实际送达。

**隐私与运行：**通知原文只当数据，不当指令；保存必要的证据，不在运行日志记录密钥或完整私聊。机器人和提醒循环各只启动一次，网页不重复启动后台。演示可显示“查了什么、结果是什么”，不显示模型内部思考。

## 四、三人分工与冲刺

| 成员 | 负责 | 首个可验收结果 |
|---|---|---|
| A：企微与 Agent | 私聊收发、通知与目标意图、工具选择、确认回复、计划表链接 | 手机企微发消息，机器人回复能打开的测试看板链接 |
| B：数据与执行 | 课表/任务/目标状态、规则排程、变更预览、版本确认、提醒队列 | 一门考试能排程，确认后实际更新数据并可重查 |
| C：网页与演示 | 手机看板、通知证据和前后差异、脱敏样例、验收与答辩 | 网页显示测试用户自己的课表和任务，并能读到更新 |

A、B、C 第一天约定用户身份、通知候选、计划草稿、确认编号、看板链接及返回结果的格式。第二天开始用同一份样例联调。真实通知、用户数据和密钥不进仓库。

| 日期 | 里程碑 |
|---|---|
| 11/20—11/21 | 验证企微私聊、链接打开及网页身份校验；打通共享测试数据；确定备用路线 |
| 11/22—11/23 | 文本通知 → 摘要 → 确认 → 看板；跑通一门考试初始计划 |
| 11/24—11/26 | 调课/改期影响、部分进度和不足协商；确认后新版本可在网页查到 |
| 11/27—11/29 | 检查提醒失效、重复通知、过期确认、跨用户隔离；做对照与小范围试用 |
| 11/30—12/1 | 只补不影响主线的增强项；12/1 冻结功能 |
| 12/2—12/5 | 回归、演练、录制备用视频、打包和 README；只修阻断问题 |
| 12/6 | 按正式赛事要求提交 |

若进度落后，先缩页面和文件格式，再删主动推送、估时等增强项。保住“贴通知、确认调整、回复链接、网页见结果”和至少一个真实的局部重排场景。

### 联调时用三次交付检查进度

| 交付 | 三个人一起验证什么 | 完成标准 |
|---|---|---|
| ① 通道跑通 | A 用企微回链接，B 提供测试数据，C 做手机页 | 手机能打开自己的看板；另一账号看不到该用户数据 |
| ② 数据跑通 | A 生成通知预览并接确认，B 提交变更，C 展示前后差异 | 同一条通知确认前不改，确认后企微回复和网页都能核对结果 |
| ③ Agent 跑通 | A 根据结果选择追问或重排，B 算冲突与缺口，C 复核展示 | 换一个截止或空档，结果跟真实数据变；不是固定演示台词 |

| F · 网页看板 | 手机优先，用同一后台显示任务、课表、学习块、计划版本与通知来源。已确认与待确认分开；测试从企微点开和未授权访问，不做第二套日常对话流程。 |
| G · 验收 | 用脱敏样例检查真实工具路径和数据变化，重点查旧通知、重复确认、跨用户看板、过期草稿、旧提醒失效与失败回滚。只报告实际测试结果。 |
| H · 答辩 | 用真实实现串起贴通知、冲突判断、确认更新、索取链接和打开看板。用工具结果与前后数据佐证，不虚报企微送达、试用人数或学习效果。 |

**第一天可直接使用的提示词：**

```text
本轮只做 UniPulse 的企微固定回复，不接模型、排程或真实校园数据。
按官方 SDK 示例读取本地配置，收到测试私聊“你好”回复“收到”。
提供不含真实密钥的配置样例和启动说明；没有机器人凭据时明确标为未实测。
固定回复实测通过后，再单独做“发一下计划表”回测试看板链接。
```

每次让 AI 完成一个小任务，并交付“改了什么、怎样运行、怎样验证、还有什么没测”。第一阶段只需要三个可检查结果：企微回固定消息、网页读测试课表、后端能算一处冲突；不要直接让 AI 一次生成整个项目。

## 六、首版验收

- [ ] 在企微私聊粘贴通知即可收到摘要，不用先开网页；缺关键信息会追问，重复或旧通知不会覆盖最新安排。
- [ ] 初始计划使用真实课表和任务；时间不足时报告未排入分钟，用户选择后重新检查。
- [ ] 调课或改期只影响相关安排，部分完成只重排剩余工作；固定课表、锁定事项和已完成工作不会被擅改。
- [ ] 确认后查得到真实数据；取消不应用草稿，过期确认被拒绝，重复确认不重复写入，失败不造成部分更新。
- [ ] 在企微说“发一下计划表”，手机能打开自己的看板，看到当前任务、课表与已确认的新计划；其他用户无法读取这份数据。
- [ ] 已过时的提醒失效；入队、发送失败和真实送达分别记录；不把模拟结果当作实际功能。
- [ ] 另一台电脑能按 README 启动；若走网页备用路线，明确这不等于已通过企微端到端验收。

### 先准备这些可重复测试的场景

| 测试输入 | 应观察到的结果 |
|---|---|
| 完整的作业通知 / 只有“下周交”的通知 | 前者生成含截止和证据的待办预览，后者追问，不猜日期 |
| 同一课程有两次候选 / 两条通知前后冲突 | 让用户选择或核对来源，原安排不变 |
| 单次调课与复习相撞 / 只换教室 | 前者局部重排，后者在不影响时间或通勤时不动复习 |
| 考试提前且时间不足 / 学生不接受任何调整 | 正确显示缺口；不把仍不可行的草稿标为完成 |
| “做了 8/20 题” / “学了 30 分钟” | 前者记录明确完成量，后者只记录用时，不据此扣减工作量 |
| 确认前课表已变 / 提交失败 | 前者要求重做预览，后者不写入部分数据、不回复成功 |
| 同一条消息再次送达 / 确认两次 | 不新增重复事项，不重复写入 |
| 甲转发自己的看板链接给乙 | 不暴露甲的数据；甲确认修改后再打开，可见最新已确认版本 |

**评估：**用同一组样例对比“直接让模型给文字计划”和 UniPulse，记录约束违规、改错对象、必要追问、人工纠错和数据一致性。试用与对照只报真实样本和失败情况，不推断成绩提升。

每组样例保留**初始课表与任务、用户原话、期望改动与保留项、实际数据库和网页结果**。判断成功不要求回复措辞一致，但应检查对象、约束、版本和最终状态。若对照的是文字计划，不把它未做实际写入算成“写入失败”，单独说明两者能力范围。

## 七、三分钟比赛演示

### 用一套可复现的数据讲清楚

固定测试时间为 2026 年 11 月 30 日上午，时区为北京时间。机器学习考试原定 **12 月 4 日 14:00**，学生每天最多学 90 分钟。样例中有三段空档：

| 可用时段 | 原计划 | 分类 |
|---|---|---|
| 11 月 30 日 19:00–20:00（60 分钟） | 复习第三章 | 必做 |
| 12 月 1 日 19:00–20:30（90 分钟） | 复习第四章 | 必做 |
| 12 月 2 日 15:00–16:20（80 分钟） | 附加模拟练习 | 选做 |

学生粘贴通知：“机器学习期末考试提前至 **12 月 2 日 14:00**，复习范围不变。”第三段空档落在新考试之后：应从样例算出 **剩余 230 分钟 → 能排 150 分钟 → 缺 80 分钟**。Agent 先说明影响，可以询问是否还有额外可用时段，或请学生确认移出这 80 分钟选做内容。主线选择后者；复核后保留两项必做任务，移除选做时间块，网页显示考试新时间与新计划版本。

样例内只开放上表三个学习时段；更换考试时间或开放时段后，缺口应随输入变化，不能把 80 分钟写死在回复里。

| 时间 | 演示 |
|---|---|
| 0:00—0:35 | 在企微交代单门考试目标及每天 90 分钟上限，生成并确认经过空档检查的初始计划 |
| 0:35—1:20 | 将一条考试提前通知粘贴到同一私聊，展示原文证据、日期变化和受影响任务 |
| 1:20—2:10 | 显示时间缺口，学生选择增加可用时段或减少选做内容；复核后在企微确认 |
| 2:10—2:45 | 在企微说“发一下计划表”，点开看板，核对新时间块、保留项和计划版本 |
| 2:45—3:00 | 用真实记录说明“为什么改、实际改了什么、哪些没改”，交代首版边界 |

准备可重置的具体日期课表、原/新通知、部分进度和不可行样例。备用展示单次调课只影响一节课，或旧通知不会回退。若企微接入失败，用网页演示同一业务流程并如实说明缺失的跨端环节。

**答辩时展示三样证据：**企微原通知与确认记录、计划表前后对比、实际工具结果（查了什么、排进多少、提交了哪个版本）。如果被问“跟普通通知机器人有什么区别”，直接指出：它把新通知跟人、课表和原目标对上，只改受影响的工作，时间不够还会问用户怎么取舍。

**参考与取舍：**用 [WorkWizee](https://github.com/microsoft/AI_Agents_Hackathon/issues/587) 参考聊天调用业务工具，用 [Motion](https://usemotion.com/help/time-management/auto-scheduling) 参考时间约束；只借鉴思路，不照搬功能。赛事评分以本次正式要求为准。

## 八、第一天就做什么

- [ ] **A（企微）**：确认测试组织和机器人权限；用手机发送“你好”收固定回复，再验证测试看板链接。
- [ ] **B（数据）**：准备两个脱敏测试用户、一周具体日期课表、一个考试与几条待办；能查出某条新安排撞了哪个时间块。
- [ ] **C（网页）**：做手机可读的任务/课表看板；准备原通知、改期通知与可重置场景；确认在手机企微内能开页面。
- [ ] **联合联调**：用同一测试用户跑“企微回链接 → 手机打开看板”，改一条测试任务后重新打开核对；记录哪些步骤还靠测试数据。第二阶段才接“贴通知 → 预览 → 确认”。

### 卡住时先查哪里

| 卡点 | 先做什么 |
|---|---|
| 无法创建机器人或收不到私聊 | 先核对组织、机器人配置与测试成员；业务开发用网页备用入口继续 |
| 电脑上能打开，手机点不开 | 检查手机能否访问部署地址，先拿不含私人数据的测试页验证，不把本机地址当作跨端成功 |
| 模型提取结果不稳定 | 先只做调课、改期、截止三类脱敏样例；要求提供原文证据，缺失留空并追问 |
| 调课后网页没变化 | 先查确认有没有真正提交，再核对网页读取的是同一用户和当前生效版本 |
| 时间不够做全套 | 保留企微收通知、确认更新、看板链接与至少一个真实重排；主动提醒和其他加分项可以不做 |
