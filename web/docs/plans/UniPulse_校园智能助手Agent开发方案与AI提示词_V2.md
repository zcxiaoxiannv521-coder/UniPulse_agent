# 一、项目定位

## 1.1 项目名称

**UniPulse——懂通知、会对账、能跟进的校园智能助手 Agent**

一句话介绍：

> 将学生主动提交的校园通知和课程资料转化为有来源、可确认、可更新的个人日程与行动任务，并在合适的时间提醒和跟进。

参赛方向为生活赛道中的“学习规划与备考、校园服务与办事”。第一版以考试、作业、调课通知为核心；社团活动作为相同事件模型的扩展示例。求职简历、健康管理、完整社团运营暂不进入本轮开发。

## 1.2 要解决的问题

- 通知散落在不同消息和文件中，学生需要反复翻找。
- 调课、改期和地点变更可能让个人日程失效。
- 转发顺序与通知发布时间不同，旧截图可能晚于新通知出现。
- 学生知道截止时间，却没有拆分出下一步要做什么。
- 提醒只响一次后就被忽略，反复催促又容易造成负担。

**主要用户：**同时管理多门课程考试、作业和临时安排的学生。第一轮试用建议招募 5—10 名目标学生，使用经授权或脱敏的真实资料。

## 1.3 第一版核心功能

| 功能 | 用户操作 | 系统结果 | 优先级 |
|---|---|---|---|
| 网页与企微对话入口 | 网页提问；测试租户私聊机器人 | 查询或调用实际业务工具 | 网页 P0；企微第一天验证 |
| 校园通知录入 | 粘贴通知文字 | 提取事件和原文证据，确认后保存 | P0 |
| 课程资料导入 | 上传可复制文字的 PDF / DOCX | 提取课程与有明确依据的事件 | P0 |
| 新旧通知对账 | 提交改期、改地点或取消通知 | 找到候选，展示差异，确认后更新 | P0 |
| 个人日程与任务 | 查询、标记完成、取消 | 保存真实状态及变更记录 | P0 |
| 基础到期提醒 | 选择提前时间或稍后提醒 | 到点发送；改期、取消后旧提醒失效 | P0（优先验证可用渠道） |
| 学习任务拆分 | 基于考试及可用时间请求计划 | 生成可调整的建议，确认后转任务 | P1 |
| 截图理解与温和跟进 | 提交通知截图；开启跟进 | 校对识别结果；按偏好少量跟进 | P1 |

**核心特色：校园通知自动对账。**

> 原通知：机器学习期末考试 12 月 2 日 14:00，A101。  
> 新通知：考试调整至 12 月 4 日 14:00，地点不变。  
> 系统：定位同一考试，展示时间差异和来源；确认后更新考试，撤销旧提醒，创建新提醒。  
> 随后导入旧截图：识别为重复或冲突信息，不自动回退。

第一版所有考试时间、截止时间、取消事项的修改都需明确确认。模型给出的高置信度不能替代用户确认或来源证据。

# 二、产品形态与使用流程

## 2.1 产品形态

采用“企微日常入口＋网页个人工作台”。网页可独立运行；企微接入不阻塞核心业务开发。

### 企业微信：低负担对话入口

- “这条通知帮我记一下。”
- “我接下来两周有哪些考试？”
- “机器学习考试改到 12 月 4 日了。”
- “复习第三章完成了。”
- “今晚 8 点再提醒我。”

借鉴提醒猫的自然表达和温和反馈，但保留 UniPulse 自己的名称与视觉。语气可在“简洁”和“陪伴”间切换，不必先开发宠物动画。

### 网页：个人工作台

| 页面 | 主要内容 | 第一版重点 |
|---|---|---|
| 今日概览 | 今日任务、待确认变更、近期安排 | 先看需要处理的事项 |
| 通知中心 | 粘贴通知、导入文件、原文与提取结果 | 来源可查、结果可改 |
| 我的日程 | 考试、作业截止、活动列表 | 时间含义明确 |
| 我的课程 | 课程及导入资料 | 不编造课程信息 |
| AI 助手 | 自然语言查询和任务操作 | 工具实际执行后才报告成功 |
| 提醒设置 | 免打扰、跟进开关、提醒渠道 | 由学生控制提醒强度 |

变更记录可先作为通知或事件详情的一部分，不必独立做一个复杂页面。

## 2.2 典型用户流程

**流程 A：导入课程资料**

1. 上传文字型 PDF / DOCX。
2. 显示提取进度；无文本时提示扫描件暂不支持。
3. 展示课程信息和事件候选，每项附页码或原文片段。
4. 未注明考试日期时保存为空，不能根据章节或教学周猜测。
5. 学生校对并确认保存，可逐条排除错误候选。

**流程 B：处理新通知**

1. 接收文字，记录原文、来源及接收时间。
2. 提取事件、适用范围、通知发布时间及证据。
3. 判断是新增、重复、修改、取消或冲突。
4. 展示确认操作；缺失信息先询问。
5. 确认后在同一事务内更新事件、记录历史、撤销旧提醒并生成新提醒。
6. 保存成功后回复明确结果，失败则保留待处理状态。

**流程 C：自然语言查询**

1. “下周有哪些考试？”由服务端计算日期区间。
2. 工具只查询当前认证用户的数据。
3. 返回事项、日期、地点和来源；无记录时说明当前资料未收录，不能推断学校没有安排。

**流程 D：任务执行与提醒**

1. 基于考试或用户输入创建个人任务。
2. 学生确认提醒时间。
3. 常驻后台发送提醒，并记录平台返回结果。
4. 学生选择完成、稍后提醒或取消。
5. 已完成和已取消任务不再跟进；没有回复不自动判定未行动。

## 2.3 关键交互规则

- 一张确认卡只对应一次操作，展示事项、旧值、新值、来源和确认按钮。
- 纯文字渠道使用明确编号，例如“确认修改 #A103”；不要只依赖“确认”二字。
- 待确认操作设有效期（建议 30 分钟），到期或目标记录版本变化时重新核对。
- 群聊不展示私人任务和完整个人日程；提示进入私聊或网页查看。
- 一个输入可拆多项，但每项独立校验；不明确的事项存草稿。
- 第一版画面使用示例数据，只演示页面、确认、完成和提醒偏好的交互，不代表已完成后台接入。

# 三、技术架构：一个主 Agent＋业务工具＋持久化提醒

## 3.1 推荐架构

```text
学生 ── 企业微信智能机器人（官方 Python SDK）
  └── Streamlit 网页（上传、校对、日程）
                │
          统一业务入口 / FastAPI
                │
          UniPulse 主 Agent
        理解意图、选工具、组织回复
                │
    通知/课程解析 ─ 事件对账 ─ 任务与确认
                │
             SQLite
     来源、事件、任务、提醒、操作与历史
                │
     唯一常驻提醒程序扫描到期记录
                │
       官方 SDK 主动推送并记录结果
```

## 3.2 职责边界

- 大模型：意图理解、信息抽取、候选匹配解释、计划建议和自然回复。
- Python：日期区间、用户权限、规则校验、字段差异、事务、状态流转和提醒发送。
- 数据库：持久事实与状态。聊天上下文不能代替数据库。
- 渠道适配层：收发消息，不另写一套独立业务逻辑。

不创建多个独立 Agent，不让模型生成 SQL 或直接执行数据库修改。所有写入通过受限业务工具。

## 3.3 技术栈

| 层次 | 推荐技术 | 说明 |
|---|---|---|
| 主语言 | Python | 统一三人开发环境 |
| 企微 | 官方 wecom-aibot-python-sdk | 长连接、收发、重连、卡片 |
| 后端 | FastAPI＋共享服务层 | 网页与机器人调用同一业务 |
| 网页 | Streamlit | 快速交付；前端原型用于讨论布局 |
| 模型 | 团队可稳定调用的 API | 结构化输出；真实文件先脱敏 |
| 文件 | PyMuPDF、python-docx | 优先可提取文字的资料 |
| 校验 | Pydantic | 日期、枚举、必填项及输出校验 |
| 数据库 | SQLite | 单机、小规模试用；参数化查询 |
| 调度 | 单实例定时扫描；可选 APScheduler 3.x | 提醒以数据库记录为准 |
| 协作 | Git＋GitHub 私有仓库 | 锁定依赖，每日集成 |

第一版采用唯一后台进程承载机器人连接和提醒循环。Streamlit 页面重跑时不得重新启动机器人或调度器；禁止多人用同一个 BotID 同时连线上环境。

## 3.4 企业微信测试策略：官方长连接优先

截至本次修订核对，官方长连接文档支持主动推送 `aibot_send_msg`，但用户需要先在对应会话向机器人发消息；同一机器人只能有一条有效长连接。单聊和群聊 @ 不等于监听所有普通群消息。

官方入口：

- [智能机器人长连接](https://developer.work.weixin.qq.com/document/path/101463)
- [Python SDK](https://github.com/WecomTeam/wecom-aibot-python-sdk)

**第一天必须验证：**

1. 测试租户能否创建 API 模式智能机器人并获取 BotID / Secret。
2. 使用官方 SDK 建立连接，私聊收消息并回复。
3. 用户先发消息后，测试一分钟后的主动推送。
4. 验证群聊 @、图片和文件；记录实际可用范围。
5. 验证掉线重连和第二连接挤掉旧连接的表现。

普通微信外部联系人、自建应用、智能机器人和微信客服是不同路线。微信客服发送受回复窗口和数量限制，不能直接视为长期任意提醒通道。不要宣称已接入学校全部群聊或普通微信所有联系人。

**11 月 21 日前必须得到可用或不可用的结论。**不可用则继续网页核心，使用日历文件导出作提醒替代方案，清楚标注推送尚未接通。测试企微不代表学校官方授权。

# 四、Agent 工具设计与数据结构

## 4.1 主 Agent 的职责

1. 判断输入属于通知、查询、修改、完成任务、提醒调整或学习规划。
2. 将材料视为待分析数据，不能执行材料里夹带的指令。
3. 使用服务端注入的用户身份，不接受模型或客户端指定其他用户身份。
4. 调用工具，处理缺失信息和操作确认。
5. 只有工具成功执行后才能回复“已保存”“已修改”。
6. 超时或模型格式错误时返回可恢复的失败结果。

## 4.2 第一版工具接口

```python
# ctx 由服务端生成，含认证身份、渠道、时区、会话标识；模型不能修改
parse_notice(text, source_meta, ctx) -> ParseResult
parse_syllabus(file_ref, ctx) -> ParseResult
query_events(date_range, ctx) -> list[Event]
match_existing_event(candidate, ctx) -> MatchResult
prepare_action(action_type, candidate, ctx) -> PendingAction
confirm_action(action_id, expected_version, ctx) -> ActionResult
query_tasks(date_range, ctx) -> list[Task]
complete_task(task_id, expected_version, ctx) -> ActionResult
snooze_reminder(reminder_id, remind_at, ctx) -> ActionResult
get_change_history(event_id, ctx) -> list[EventChange]
generate_study_plan(event_id, availability, ctx) -> PlanDraft
```

确认操作不能通过模型口头表示“用户已确认”绕过；服务端必须验证当前用户的明确交互和 action_id。为工具设置白名单、调用次数上限与超时。

## 4.3 统一事件 JSON 格式

```json
{
  "event_id": "evt_ml_final",
  "course_name": "机器学习",
  "course_section": "教学一班",
  "event_type": "exam",
  "title": "机器学习期末考试",
  "start_time": "2026-12-04T14:00:00+08:00",
  "end_time": null,
  "due_at": null,
  "time_precision": "minute",
  "timezone": "Asia/Shanghai",
  "location": "A101",
  "status": "active",
  "version": 2,
  "source_id": "notice_002",
  "needs_confirmation": true,
  "evidence": [{"field": "start_time", "quote": "考试调整至12月4日14:00", "page": null}]
}
```

规则：

- 活动开始与作业截止分开：考试用 start_time，作业用 due_at。
- 只知道日期时，精度为 date，不补成零点或晚上 23:59。
- 相对日期依据原消息发布时间；发布时间未知时显示假设或请求确认。
- “第 16 周”需要校历；“每周三”需要重复规则。第一版可明确暂不支持，保存原文待处理。
- 事件的 end_time 未知时不自行推断时长；冲突检测说明信息不足。
- 每个关键字段保留原文片段，资料保留页码。
- confidence 如保留，仅为辅助信息，不用于自动放行高影响修改。

**字段级修改使用补丁：**

```json
{
  "action_type": "update_event",
  "target_event_id": "evt_ml_final",
  "expected_version": 1,
  "changes": {"location": "B203"},
  "explicit_clear_fields": [],
  "source_id": "notice_003"
}
```

未提到的字段不出现在 changes 中；明确清空的字段单独列出并确认。不能用解析结果的 null 覆盖原日期、时间或地点。

## 4.4 数据库建议

| 表 | 核心字段 | 作用 |
|---|---|---|
| users | id、display_name、timezone、quiet_hours、followup_enabled | 用户及提醒偏好 |
| channel_bindings | user_id、channel、tenant_id、external_user_id、chat_id | 可信渠道身份映射 |
| courses | id、user_id、name、section、teacher | 课程及教学班 |
| notices | id、user_id、original_text、file_ref、published_at、received_at、source_label、content_hash | 原始材料、来源和去重 |
| events | id、user_id、course_id、type、title、start_time、end_time、due_at、time_precision、status、version | 当前校园事件 |
| event_sources | event_id、notice_id、evidence_json | 一个事件关联多个来源 |
| tasks | id、user_id、event_id、title、due_at、estimated_minutes、status、version | 个人行动任务 |
| reminders | id、user_id、event_id、task_id、target_version、remind_at、state、attempts、last_error、sent_at | 持久提醒队列 |
| pending_actions | id、user_id、target_id、expected_version、payload、expires_at、state | 明确确认与幂等执行 |
| event_changes | id、event_id、old_data、new_data、source_notice_id、changed_at | 历史及撤销依据 |
| processed_messages | channel、tenant_id、msgid、state | 消息排重，唯一联合约束 |

按需用短字符串 ID 或整数，不追求复杂设计。所有对象访问都验证所属用户；关联表需通过其父对象验证权限。提醒中的 event_id / task_id 至少存在一个并与当前用户一致。

## 4.5 通知对账规则

1. 同消息 ID 重试只处理一次；相同材料重复导入不重复建事项。
2. 同课程不代表同事件，区分期中、期末、小测和补考，以及教学班。
3. 接收时间不代表发布时间；后转发的旧通知不能自动覆盖新安排。
4. “新增补考”按新增候选；“取消考试”按取消候选；“地点改为……”按字段补丁。
5. 来源冲突或无法判断先后时保留双方证据，让用户决定。
6. 确认时校验记录版本；版本已变则原确认失效，重新生成差异。
7. 同一事务完成事件更新、历史记录、旧提醒失效和新提醒生成。

## 4.6 提醒可靠性与任务状态

任务状态：todo / doing / done / cancelled。  
提醒状态：pending / sending / sent / failed / invalidated。

- 发送提醒不代表任务完成；接口成功也不表示用户已读。
- 发送前再次检查目标状态及版本，取消和过时提醒不发送。
- 失败有限次重试；结果不明时标记待核查，不能承诺绝对不重复或绝对送达。
- 单实例运行，数据库中原子领取待发记录；重启恢复超时 sending 记录并按策略核对。
- 超过补发宽限（建议 30 分钟）不轰炸式补发，可合并到下次摘要；策略允许用户调整。
- 默认不开启重复督促；用户开启后每任务每日最多跟进 1 次，完成或取消立即停止。
- 免打扰默认 22:30—08:00；窗口内非紧急提醒顺延，并提示实际提醒时间。
- 机器休眠、程序退出期间无法实时发送；持续服务须运行在常在线设备，演示前关闭休眠。

# 五、三人分工与协作方式

## 成员 A：企业微信接入、主 Agent 与确认流程

任务：官方 SDK 最小验证；统一消息上下文；意图与工具调用；多轮澄清；确认卡及 action_id；连接与模型错误处理。

交付物：wechat_bot.py、agent.py、llm_client.py、confirmation_service.py、最小收发与工具调用示例。

## 成员 B：事件模型、数据库、通知对账与提醒

任务：数据表与校验模型；新增查询；匹配与字段补丁；版本和事务；提醒扫描与状态；高风险业务测试。

交付物：schemas.py、database.py、schedule_service.py、matching_service.py、reminder_service.py、关键用例。

## 成员 C：网页、文件提取、产品体验与验收

任务：Streamlit；PDF / DOCX 文本提取；结果校对页面；通知、日程及任务展示；演示资料；验收记录、README 和录屏。

交付物：app.py、pages/、file_parser.py、演示数据、验收清单与说明。

## 三人必须共同遵守的协作规则

1. 第一天约定 ctx、结构化事件、工具错误格式和数据库迁移方式。
2. 第二至第三天跑通一条“文字通知→确认保存→查询→改期”的小流程。
3. 每天合并一次，接口变更先同步；锁定依赖版本。

# 九、验收标准：什么叫“真的做完了”？

## P0：必须通过

- [ ] README 可指导另一台电脑启动网页和后台。
- [ ] 文字通知可解析、校对、确认保存并查询。
- [ ] PDF / DOCX 可提取课程信息，无考试日期时不会生成虚假考试。
- [ ] 正常改期展示旧值、新值、来源，确认后更新。
- [ ] 同通知重复导入不重复创建；旧通知晚到不自动回退。
- [ ] 同课程期中/期末/补考不会误合并。
- [ ] 只改地点不会清空考试时间。
- [ ] 多候选、日期不完整和来源冲突会请求澄清。
- [ ] 过期确认或旧版本确认不能覆盖新版本。
- [ ] 用户 A 无法读取或修改用户 B 的对象。
- [ ] 基础提醒经过真实渠道验证；未接通则如实展示替代方案和限制。
- [ ] 改期、取消、完成会使旧提醒失效。
- [ ] 服务重启保留任务与提醒；失败有记录和可恢复路径。
- [ ] 工具失败不会被回复成已执行；原文中的恶意指令不会执行。
- [ ] 企微不可用时仍有网页端完整核心流程。

## P1：争取完成

- [ ] 截图识别并逐项校对。
- [ ] 用户可设置免打扰、稍后提醒与温和跟进。
- [ ] 基于可用时间和考试生成计划草稿，确认后创建任务。
- [ ] 日历文件导出。
- [ ] 手机窄屏和群聊隐私提示。

## 试用与指标

建议准备至少 30 条带人工标注的脱敏通知，覆盖正常与异常样例；另请 5—10 名学生完成若干相同任务。

记录关键字段正确率、错误覆盖次数、人工确认次数、完成一条通知录入所需时间及提醒发送结果。日期字段有歧义时，正确行为可为请求澄清，不能为了提高完成率强行填值。

验收用例要求错误覆盖为零；这只是本测试集通过条件，不代表真实世界零错误。报告必须注明样本量，发送成功与任务完成分开统计。

学校全量群聊历史、正式教务系统接入、独立手机 App、复杂多 Agent、完整健康/求职模块、支付会员、宠物动画和多机集群。

# 十、演示方案与三分钟答辩结构

## 演示准备数据

1. 一份虚构教学大纲，含课程信息和一项明确安排。
2. 原通知：机器学习考试 2026-12-02 14:00，A101。
3. 新通知：调整到 2026-12-04 14:00，地点不变。
4. 原通知的重复/旧截图文本。
5. 两位演示用户，若干个人任务和一个一分钟后触发的测试提醒。

界面显示演示时间，查询区间固定且可见。演示结束可一键恢复样例数据（仅开发演示环境提供）。

## 三分钟演示流程

| 时间 | 展示内容 | 讲解重点 |
|---|---|---|
| 0:00—0:20 | 今日概览 | 通知改变后，个人安排容易失效 |
| 0:20—0:50 | 导入原通知或资料 | 真实提取、字段证据、确认入库 |
| 0:50—1:30 | 导入改期通知并确认 | 精确修改、来源和历史、旧提醒失效 |
| 1:30—1:55 | 再次导入旧通知 | 不按接收顺序回退、不误覆盖 |
| 1:55—2:30 | 查询近期安排、提醒、任务完成 | 持续状态和实际工具执行 |
| 2:30—3:00 | 说明结果与边界 | 核心价值、试用证据、测试租户范围 |

答辩表达：

> UniPulse 将校园材料转为有依据的个人事件。收到变更后，它定位相关安排，展示差异，在确认后更新日程和提醒。学生还可以通过聊天查询、完成任务或调整提醒。每个关键动作都有真实工具和持久记录。

未完成的企微入口、OCR 或学习计划必须从成果介绍中移除，不能用原型画面代替真实功能演示。

| 旧通知、同名考试误匹配 | 覆盖有效安排 | 保留发布时间、教学班、证据和确认 |
| 日期/字段抽取错误 | 误排日程 | 精度、原文校对、结构化校验 |
| 重复连接或多个调度器 | 掉线、重复提醒 | 唯一后台实例，网页不启动后台 |
| 发送结果不明或停机 | 漏发或重发 | 记录、有限重试、补发策略，说明运行条件 |
| 群聊或身份绑定错误 | 私人数据暴露 | 后端身份、私聊查询、所属对象验证 |
| 大文件/扫描件解析失败 | 导入受阻 | 第一版限制文件大小与类型，错误可恢复 |
| B 的任务积压 | 核心延期 | C 承担文件提取，A 承担确认流程，早期联调 |
| 模型网络不稳定 | 演示卡顿 | 超时与重试边界、真实缓存样例、备用录屏 |

# 最后的开发原则

> 学生交来通知 → 系统提取并核对来源 → 展示需要确认的操作 → 实际更新个人安排 → 同步提醒 → 学生查询与执行。
